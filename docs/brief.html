交付说明

按题目的交付要求逐条对应，几分钟读完；每节末尾链接到详细设计。

一句话：原件只追加不覆盖，每个字段都能追回到“文件 · 工作表/页 · 行 · 列”；只有跨供应商、共用 OE 且关键属性全部一致的记录才自动归一，其余一律进入人工复核，并写明原因、冲突、缺失和建议动作；人工决定优先于规则、可审计、可撤销。

2. 数据结构与处理流程

数据分三层，职责互不混淆：

层模型特点
证据层Supplier · SourceFile（原件）· ImportBatch（导入批次）· SourceRecord（每一行原值 + 定位）只追加，永不修改；是一切结论的依据
档案层SupplierItem（供应商条目，身份 = 供应商 + 编号）· FieldValue（字段级来源）· PartNumber（编号检索）· SupplierOffer（报价）· Product（归一产品）由证据 + 规则推导，可重算；每个值都指回 SourceRecord
判断层MatchCandidate（候选对）· Issue（异常）· ReviewDecision（审计日志）规则决定可随规则刷新；人工决定单独保存、优先生效

任何一步发现的问题（无法解析、缺字段、位置矛盾、关键属性变化……）都记为带定位的 Issue，不静默丢弃、不猜测填充。详见 ER 图 与 流程。

3. 哪些自动处理，哪些必须人工判断

系统自动处理

情况处理样本例子
表头写法不同但在别名表内自动映射列；未识别列保留原值并在报告中列出A 的 Supplier SKU / B 的 Brand Number / C 的 Part #
名称写法、单位、符号差异归一化：类别、左右、车型年份、mm→cm、$→USD（推断会记提示）Side Grille, Left side = Left Side Grille；1220 x 750 x 70 mm = 122 x 75 x 7 cm
同一文件再次导入按 sha256 识别为重复，不产生任何变化重复导入 A 原表
新资料中的新增 / 未变 / 报价变化新增建档；报价追加为新的一条，旧报价保留为历史A v2 中 A-001 调价、A-002 改 MOQ
自动归一仅当跨供应商、共用 OE，且类别、车型（含年份）、尺寸、位置全部存在并一致A-001 ↔ B-001 等 12 对；C-1001 并入同一产品
自动排除无共同 OE，且类别 / 位置 / 车型 / 尺寸有硬冲突：不进人工队列，但在 Admin 可查排除理由A-008 空滤壳 vs A-010 风扇护罩（同车型同尺寸）

必须人工判断

情况为什么不能自动样本例子
共用 OE，但类别 / 左右 / 尺寸冲突可能是 OE 录错，也可能是通用参考号；合并会发错货OE-SHARED-01：A-021 Front Grille vs B-019 Bug Screen
共用 OE，但缺关键字段证据不足以排除冲突C-2005 缺尺寸；B-013 缺尺寸和年份
无 OE，仅类别 / 车型 / 尺寸一致“长得像”不等于同一件A-013 vs A-001
属性一致但 OE 不同可能是不同代次或替代件A-001 vs A-021
同一供应商的两个编号可能是重复录入，也可能是不同品质档A-005 vs A-028（同 OE 同属性）
会造成传递合并A≈B、B≈C 不代表 A≈CB-005 ↔ A-028 会把 A-005、A-028 带进同一产品，被暂停
已归一的记录关键属性变了原来的证据失效A v2 中 A-006 尺寸变化，与 B-006 的归一被重新打开
缺字段、类别无法识别、位置来源矛盾、日期有歧义系统不猜测填充A-025 缺车型尺寸 OE；A-030 “Hood Latch”；C-9001 只写 “Grille”
撤销一条自动归一规则也可能错产品页进入该关系，选“不是同一产品”即拆分

4. “疑似同一产品”的判断依据、风险控制与确认入口

判断依据

  1. 候选生成：只比较共用 OE、同类别同车型、或同尺寸的记录；编号字符串本身从不作为依据（样本中 A-01-00 / B01X 的数字只是巧合）。
  2. 逐字段比较：OE、类别、车型、尺寸、位置各得出 相等 / 冲突 / 缺失 / 不适用；名称相似度只作弱证据，不单独触发或否决。
  3. 置信度 = 相等字段权重 ÷ 所有适用字段权重（OE 40、类别 20、车型 15、尺寸 15、位置 10、名称 5）；缺失字段计入分母，所以“无 OE 仅属性一致”不会显示为高置信；有硬冲突时置信度封顶 0.3。

风险控制

  • 硬冲突一票否决：类别、左右、车型年份、尺寸任一冲突，永不自动合并。
  • 同供应商不自动合并，并在聚类时防传递：规则产生的合并若会把冲突记录或同供应商的两个编号放进同一产品，就暂停并交人工。
  • 人工决定优先：以双方属性指纹（evidence_hash）为准；资料未变，人工决定一直有效；资料变了自动重新打开并写审计。
  • 可解释、可复现：每个候选记录原因码、冲突字段（双方取值）、缺失信息、建议动作和规则版本；规则参数在 config/rules/matching.yaml，带版本号。
  • 可撤销、可审计：所有决定（含规则首次决定与系统重新打开）写入只追加的 ReviewDecision。
  • 自动化测试守护：样本中的每一类陷阱都有端到端测试，保证“误合并 = 0”。

人工确认入口

入口用法
Web 复核队列 /review/按优先级（共用 OE 冲突最先）排列；详情页并排显示字段对照、双方原始行、建议动作；可选 确认合并 / 不是同一产品 / 待补充资料。对有硬冲突的候选确认合并时必须填写理由。
产品详情页列出每条已合并关系，可进入后拆分
xlsx 离线回写导出 review_list.xlsx → 填 decision / note → import_review 文件 --reviewer 姓名；任一行有误则整份不写入并逐行报错
Admin候选批量决定；证据数据只读

5. 如何保留原始文件及字段来源

层级做法演示时看哪里
原始文件按内容 sha256 存到 originals/<sha256>/原文件名，只写不改；同名不同内容不会互相覆盖，同内容重复导入直接识别导入批次页“下载原件”；自动化测试校验原件哈希前后一致
原始行每次导入的每一行保存为 SourceRecord：按原列顺序的原值 + 定位（工作表·行 或 页·表·行）+ 行哈希条目详情页“原始行（每次导入的观察）”
字段FieldValue 记录每个字段的原值、归一值、来源行、来源列；值变化时旧值标为历史，不删除条目详情页“字段级来源”；master_data.xlsx 的“字段来源”表
报价每家、每次报价单独一行，原币种原样保存、不换算；新报价追加产品页分供应商报价；supplier_offers.xlsx
判断候选、异常都带来源定位；决定写审计日志（人、时间、渠道、备注、快照）候选详情页“审计记录”

所有导出文件每一行都带来源定位，例如 候选人材料_供应商A报价表.xlsx!报价明细!R14、供应商C目录.pdf!p2!t1!r1。

6. 后续新增资料如何持续维护

场景做法
新供应商 / 新格式import_source 文件 --supplier D --dry-run 预览列识别 → 未识别的列在 config/rules/column_aliases.yaml 补别名，或写 --mapping 映射文件 → 正式导入。网页 /imports/ 也可上传。
同一供应商的新版本直接导入：系统按“供应商 + 编号”判定 新增 / 未变 / 更新 / 冲突 / 本次未出现（不删除）；关键属性变化会重新评估相关归一，并进入复核队列。增补文件加 --partial，不做“未出现”判定。
规则调整改 synonyms.yaml（新品类、新写法）或 matching.yaml（权重、容差、自动归一条件）并提升 version → run_matching --dry-run 查看会变化的候选 → run_matching 正式执行；人工决定不受影响。
人工确认回写在线 /review/；或离线 export_data --only review → 填写 → import_review。回写后自动重新聚类。
规则沉淀复核中反复出现的写法补进别名 / 同义词表，下次由规则直接识别，人工量逐步下降。

8. 演示路线（约 10 分钟）

  1. 数据结构与流程（2 分钟）：本页第 2 节的三层模型与流程图；运行 demo，看导入报告。
  2. 原件与字段来源（2 分钟）：搜索 OE-VNL-1001 → 产品页（A、B 两家品牌号、分别报价）→ 点一个条目 → 字段级来源、原始行、下载原件。
  3. 判断依据、风险控制、人工确认入口（3 分钟）：复核队列打开 OE-SHARED-01 候选（字段对照、冲突、建议动作）→ 选“不是同一产品”；打开 A-013 候选 → 确认合并；产品页演示拆分；Admin 看被排除的 A-008 / A-010。
  4. 自动 vs 人工（1 分钟）：对照本页第 3 节，指出刚才哪些是规则自动处理、哪些是人工决定（审计记录里可见）。
  5. 持续维护（2 分钟）：import_source samples/demo/供应商A报价表_v2.xlsx（更新 / 冲突 / 未出现，A-006 被重新打开）→ 导入 C 的 PDF → 导出 review_list.xlsx 填一行后 import_review 回写。
