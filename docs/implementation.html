分步实施文档

每一步都有产出、命令与完成标准（DoD）。步骤之间单向依赖，可逐步提交。

环境准备

本机开发

本机不单独启动数据库容器，在已有的 PostgreSQL 16 实例中建独立的库与角色：

# 1) 在已有 PG 实例中建库（示例：容器 tpdc-db-1，映射到 127.0.0.1:5441）
docker exec -i tpdc-db-1 psql -U tpdc -d postgres \
  -v pw=改成你的密码 < scripts/create_db.sql

# 2) Python 依赖
uv sync

# 3) 配置
cp .env.example .env
#   DATABASE_URL=postgres://vehicle_parts:密码@127.0.0.1:5441/vehicle_parts
#   DJANGO_SETTINGS_MODULE=config.settings.local

# 4) 初始化
uv run python manage.py migrate
uv run python manage.py createsuperuser   # 或 demo --noinput --reviewer 名字 --password 密码

Python 3.12+（uv 会按锁文件准备环境；Docker 镜像使用 3.13）。scripts/create_db.sql 创建角色 vehicle_parts（带 CREATEDB，供测试建临时库）与同名数据库，幂等可重复执行。

服务器

见 部署：compose.yaml 自带 db 与 web 两个服务。

步骤 3 · 归一化器（先写测试）

产出：apps/catalog/normalizers.py、config/rules/synonyms.yaml、tests/test_normalizers.py。

测试用例直接取自样本中的每类陷阱：

  • Air Filter Housing Cap ≠ Air Filter Housing；Side Grille, Left side = Left Side Grille；Side Grille + Right 列 + B41R → right。
  • Volvo VN ≠ Volvo VNL；Volvo VN 缺年份不算冲突；Freightliner Cascadia P3 车型为 Cascadia P3。
  • 1220 x 750 x 70 mm == 122 x 75 x 7 cm；86 x 36 x 56 与 56 x 36 x 86 排序后相等。
  • 位置三来源不一致 → POSITION_INCONSISTENT 且位置为未知。

DoD：uv run pytest tests/test_normalizers.py 全绿；归一化器不依赖数据库。

演示脚本

  1. uv run python manage.py demo --noinput --reviewer reviewer --password …：清空业务数据 → 导入 A、B → 匹配 → 导出，并创建复核账号。讲解导入报告与异常。
  2. runserver，搜索 OE-VNL-1001 → 点“导出查询结果”，打开 xlsx（查询条件、归一产品、品牌号、分别报价、字段来源、相关疑似与异常）→ 产品详情：两个品牌号、两条报价（USD/USD、不同 MOQ）→ 点开尺寸字段看来源。
  3. 复核队列（按疑似组）：打开 VNL 前格栅这一组，组内并排对照 → A-021 ↔ B-019（OE-SHARED-01）选“不是同一产品”、A-013 那一对选“确认合并”，一次提交；打开 B-025 看“疑似品名错误”；再到产品页演示“拆分”。
  4. import_source samples/demo/供应商A报价表_v2.xlsx --supplier A：展示 UPDATED / CONFLICT / NEW / NOT_IN_LATEST；A-006 只换了包装算“更新”，仍与 B-006 保持归一；A-012 改了年款算“冲突”，归一被重新打开；A-028 被防传递拦下。
  5. 规则调整演示：在 config/rules/synonyms.yaml 为 A-030 “Hood Latch” 加一个类别，运行 run_matching --dry-run 看到“按新规则重新标准化”的变化，再正式运行；A-030 得到类别，UNKNOWN_CATEGORY 自动关闭。
  6. 网页上传 samples/demo/供应商C目录.pdf（供应商 C）：在预览页看识别出的列映射与每行预计状态，确认导入；讲 PDF 页码定位、续页沿用表头、mm 换算、币种推断。
  7. export_data：打开 review_list.xlsx，填写 decision 后 import_review 回写。

部署

Docker Compose（服务器）

cp .env.example .env     # 设置 DJANGO_SECRET_KEY、POSTGRES_PASSWORD、DJANGO_ALLOWED_HOSTS
docker compose up -d --build
docker compose exec web python manage.py createsuperuser
docker compose exec web python manage.py demo --with-increment --noinput   # 可选：演示数据
  • db：postgres:16，数据卷 pgdata，healthcheck 就绪后才启动 web。
  • web：python:3.12-slim + uv 安装锁定依赖；入口脚本执行 migrate、collectstatic 后启动 gunicorn；media 卷保存原件归档。
  • 备份：同时备份 pgdata 与 media 卷（原件与数据库必须一致）。
  • 未配置 HTTPS 时在 .env 设 DJANGO_SECURE_COOKIES=false；配置 HTTPS 后可开启 DJANGO_SSL_REDIRECT 与 DJANGO_HSTS_SECONDS。

GitHub Pages（本文档）

  1. 推送到 GitHub；仓库 Settings → Pages → Source 选 Deploy from a branch，分支 main，目录 /docs。
  2. docs/.nojekyll 已存在，静态文件原样发布；无需构建。

维护手册

接入新供应商 / 新文件

uv run python manage.py import_source 新文件.xlsx --supplier D --supplier-name "供应商D" --dry-run
# 查看：识别到的表头行、列 → 字段映射、未识别列、将产生的异常
# 如有未识别列：在 config/rules/column_aliases.yaml 补别名，或写 mapping.yaml：
#   sheet: Sheet1
#   header_row: 3
#   columns: {"Mfr Part": supplier_part_no, "Desc": name, "Fits": fitment}
uv run python manage.py import_source 新文件.xlsx --supplier D --mapping mapping.yaml
# 已成功导入过的文件，想按新映射 / 新规则重新处理：
uv run python manage.py import_source 新文件.xlsx --supplier D --mapping mapping.yaml --reprocess

也可以在网页 /imports/ 上传：预览页直接逐列选择字段（留空 = 忽略），没识别出表头时填写表头行号后重新预览，确认后才入库。

调整规则

  1. 修改 config/rules/matching.yaml（权重、容差、自动确认条件）或 synonyms.yaml，提升 version。
  2. run_matching --dry-run 查看会被重新标准化的条目与分类变化摘要。
  3. run_matching 正式执行：先按新规则重新标准化所有已导入条目（字段历史保留、不再适用的异常自动关闭），再重新匹配；人工决定不受影响，只有证据变化才会重新打开。

人工确认回写

  • 在线：/review/ 按疑似组一页处理，也可逐对处理（/review/pairs/）。
  • 离线：export_data --only review → 在 review_list.xlsx 的 decision 列填写 merge / reject / needs_info（异常表填 resolve / ignore）→ import_review review_list.xlsx --reviewer 姓名。

面试现场的新资料

情况系统表现处理方式
提取错误（表头不识别、PDF 无表格、值无法解析）识别不出数据行时导入直接失败、不留归档，并提示下一步；网页预览列出未识别列与没找到表头的表的前几行；UNPARSEABLE / INVALID_VALUE 异常带页码行号在预览页逐列选择字段或填写表头行号后确认；或命令行补别名 / 写 --mapping 后重导
编号冲突（同 OE 不同件、同家编号重复）SHARED_OE_CONFLICT / DUPLICATE_KEY_IN_FILE，默认不合并复核队列中核对，写备注；需要时向供应商确认
品名与规格矛盾SUSPECTED_NAME_ERROR：包装尺寸与同车型另一类别的多条记录一致、却与同类都不同向供应商核对品名或尺寸，修正后重新导入
规格缺失MISSING_* 异常；缺关键字段不自动归一，INSUFFICIENT_FOR_MATCHING归入待补充；补齐后重新导入（CONFLICT/UPDATED 会自动触发重评）
疑似重复suspect 候选，含原因、冲突、缺失、建议动作确认 / 否决 / 待补充，决定可审计、可撤销
