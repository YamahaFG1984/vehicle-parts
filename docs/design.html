设计文档

对应 PRD v1.0 · 规则集版本 2026.09-1

1. 设计概览

整个系统围绕三条不变量设计：

  1. 证据不可变：原始文件按内容哈希归档；每次导入的每一行都保存为一条“观察记录”（原始值 + 定位），之后只追加，不修改、不删除。
  2. 整理结果可重算：供应商条目、归一产品、匹配候选都是从证据和规则“推导”出来的，规则调整后可以重跑；唯一不能重算的是人工决定，所以人工决定单独保存、优先生效。
  3. 宁可待确认，不可错合并：自动归一只发生在“有共同 OE 且所有关键属性都存在且一致”的跨供应商记录之间；其余一律给人看，并且说清楚为什么。

2. 架构

2.1 技术选型

Django 5.2 LTS

选择
Django 5.2（LTS，支持到 2028-04），ORM + 迁移 + Admin + 管理命令。
理由
数据档案类系统的主要工作是建模、约束、后台查看与人工操作；Admin 直接提供复核人可用的后台，管理命令天然适合“导入 / 匹配 / 导出”这类批处理；LTS 适合长期维护。
取舍
比 FastAPI + 前端更重，但省下了后台与认证的开发；本项目不追求界面，Django 模板足够。

PostgreSQL 而非 SQLite

选择
PostgreSQL 16，使用 JSONField（原始行）、pg_trgm（编号/名称模糊检索）、部分唯一约束、事务。
理由
原始行结构因供应商而异，JSONB 保存原样最自然；模糊检索需要 trigram 索引；多人复核与增量导入需要可靠的并发与约束。
取舍
本地开发需要一个 PG 实例：本机共用已有容器（独立库与角色），服务器用 compose 自带的 db 服务。

规则引擎 + 人工复核，而非机器学习

选择
可解释的确定性规则：候选生成 → 字段比较（相等/冲突/缺失）→ 硬冲突一票否决 → 评分 → 分类；规则参数放 YAML 并带版本号。
理由
样本极小（53 行），没有标注数据；业务要求“说明触发原因、冲突字段、缺失信息”，规则天然可解释；错合并代价远高于漏合并。
取舍
召回率依赖同义词与规则覆盖，新品类需要维护同义词；积累足够人工决定后可加入学习型打分作为辅助信号（不替代硬冲突否决）。

其他库

选择
openpyxl（读写 xlsx，保留行号）、pdfplumber（PDF 表格与页码）、django-environ（12-factor 配置）、PyYAML、rapidfuzz（名称相似度）、uv（依赖锁定）、pytest-django。
理由
不用 pandas 读取：pandas 会推断类型、丢失原始文本与行号，而本系统最看重“原值 + 定位”。
取舍
手写少量解析代码换来对原始值的完全控制。

2.3 代码约定（Django 5.2 / Two Scoops）

  • 设置拆分 config/settings/{base,local,test,production}.py；机密与连接串只从环境变量读取（.env 不入库）。
  • 业务写操作放 services.py，读查询放 selectors.py；视图与管理命令只做参数解析和调用，保持“薄”。
  • 模型用 TextChoices、UniqueConstraint、CheckConstraint(condition=…)（5.1+ 写法）、db_default；所有模型继承 TimeStampedModel。
  • 导入批次整体包在 transaction.atomic() 中；匹配重跑同样原子（--dry-run 即在事务末尾回滚）。
  • 全站登录访问：使用 Django 5.1+ 的 LoginRequiredMiddleware，登录复用 Admin 登录页；静态文件在生产环境由 WhiteNoise 提供。
  • 归一化器、比较器是无数据库依赖的纯函数，单元测试覆盖样本中的每一类陷阱。
  • 可调参数放 config/rules/：column_aliases.yaml、synonyms.yaml、matching.yaml。

3.3 模型取舍

观察记录（SourceRecord）与条目（SupplierItem）分离

选择
每次导入的每一行都是新的 SourceRecord；SupplierItem 以 (供应商, 供应商编号) 为身份，指向当前观察。
理由
同一条目会随新报价表反复出现，分离后能回答“某字段在哪一版文件里是什么值”，增量比对也只是比较新旧观察。
取舍
数据量随导入次数线性增长（对报价表规模可接受）；查询当前值需要走条目表的冗余字段。

字段级来源表（FieldValue），而非每个字段加“来源列”

选择
一行 FieldValue 记录一个字段的原值、归一值、来源行、来源列。
理由
满足“字段级来源”要求，同时保留历史；新增字段无需改表结构。
取舍
存储多约 10 倍行数、需要 join；匹配所需的当前值在 SupplierItem 上冗余一份，由服务层保持一致。

每个条目都属于一个 Product

选择
单成员产品即“独立产品”；合并就是改条目的 product 外键。
理由
搜索、详情、导出统一以产品为中心，不需要区分“已归一 / 未归一”两套查询。
取舍
产品编号可能因聚类变化而退役，用 merged_into 指针保留可达性。

候选对（pair）而非直接聚类

选择
先生成两两候选并逐对说明理由，再把确认的对聚成产品。
理由
人工决定的最小单位是“这两条是不是同一个”；逐对的原因、冲突、缺失最容易解释和审计。
取舍
对数可能较多；通过“以簇为节点生成候选”（见 5.4）控制数量。

原件内容寻址存储

选择
按 sha256 存放原件，数据库只存路径与哈希。
理由
同名不同内容的文件不会互相覆盖；同内容重复导入天然去重；哈希可用于证明原件未被改动。
取舍
原件存于文件系统（服务器上是 docker 卷），备份时需同时备份卷与数据库。

4. 处理流程

4.1 归档与提取

  • 归档：计算 sha256；已存在 → 批次记为 duplicate 并直接返回上次结果；否则复制到 originals/<sha256>/，写 SourceFile。原件路径下的文件从不被程序改写。
  • xlsx：openpyxl 只读 + data_only=True（取公式结果）；逐工作表扫描前 30 行定位表头；每一数据行记录 {sheet, row}；完全空行跳过；日期单元格保留 ISO 文本。
  • csv：自动识别编码（utf-8-sig / gbk 回退）与分隔符；定位 {row}。
  • pdf：pdfplumber 逐页提取表格（先线框策略，失败再用文本对齐策略）；跨页续表若没有表头，沿用上一页表头（列数一致时）；定位 {page, table, row}。某页无法提取出表格 → Issue UNPARSEABLE（带页码），不静默丢弃。

4.2 列映射

config/rules/column_aliases.yaml 为每个语义字段列出表头别名（忽略大小写、空格、标点）：

supplier_part_no: [supplier sku, brand number, part no, part #, item no, sku, 编号, 货号]
name:             [product description, english name, description, product name, 名称, 品名]
fitment:          [truck application, fitment, application, vehicle, 适用车型]
position:         [position, install side, side, location, 位置]
oe_numbers:       [oe / reference, cross ref, oe, oem #, oe number, 参考号, oe号]
package_dims:     [package size, package, carton dimensions, dimensions, 包装尺寸]
price / currency / moq / quote_date / source_ref / brand / category ...
  • 表头识别：候选行中命中别名最多且 ≥3 个的行即表头；supplier_part_no 必须命中，否则该表不导入并报错。
  • 未识别的列：原值仍保存在 raw_data，并在导入报告中列出，提示维护者补充别名。
  • 显式映射：--mapping file.yaml 可指定工作表、表头行、列→字段、默认品牌、是否用编号后缀推断左右等，优先级高于别名。

4.4 增量比对

身份键：(供应商, 供应商编号)。对新文件的每一行：

状态判定动作
NEW身份键从未出现建条目与单成员产品，参与匹配
UNCHANGED原始行哈希与当前观察相同只记录这次观察
UPDATED只有价格、币种、MOQ、报价日期、名称措辞变化（归一后关键属性不变）追加新报价（旧报价 is_current=False），更新字段来源
CONFLICT关键属性（类别、位置、车型、尺寸、OE）变化更新条目并写 KEY_ATTR_CHANGED Issue（新旧值）；该条目的所有候选重新评估，依赖旧证据的人工决定被重新打开
DUPLICATE同一文件中身份键重复出现第一行生效，其余记 DUPLICATE_KEY_IN_FILE
NOT_IN_LATEST该供应商上一版文件中有、这次没有不删除，标 present_in_latest=False，写 info 级 Issue

“本次未出现”只在同一供应商导入的是全量表时有意义；导入命令提供 --partial 表示增补文件，此时不做缺失判定。

5. 匹配规则

参数位于 config/rules/matching.yaml，含 version；每个候选记录生成它的规则版本。

5.1 候选生成（blocking）

只比较落在同一“块”里的条目，避免全量两两比较，同时跨供应商和同供应商内部都比较：

  • 共有规范化 OE 号（长度 ≥ 5）；
  • 相同类别 + 相同车型（make+model）；
  • 相同排序后尺寸（容差内）。

编号字符串（包括其中的数字）从不作为候选依据——样本中 A-01-00/B01X 的数字巧合只在前 12 行成立。

5.2 字段比较

每个字段比较结果为 equal、conflict、missing（一方或双方缺）或 n/a（双方都没有且该类别不需要，如无左右之分的前格栅）：

字段equalconflict权重硬冲突
OE集合有交集双方都有但无交集（软冲突 OE_DIFFER）40否
类别相同不同20是
车型make+model 相同，且年份区间相同或一方缺年份make/model 不同，或年份都有且不同15是
尺寸排序后每维差 ≤ 1 cm超出容差15是
位置相同left vs right10是
名称rapidfuzz token_set_ratio，仅作弱证据加分（×5），从不单独触发或否决5否

score = 相等字段权重之和（名称按相似度折算）；confidence = score ÷ 所有适用字段的权重和（缺失字段也计入分母，只有 n/a 除外），因此“无 OE、仅属性一致”不会显示为高置信；存在硬冲突时置信度上限为 0.3（conflict_confidence_cap）。缺失字段列入 missing。

5.3 分类决策

shared_oe   = OE 相等（有交集）
hard        = {类别, 车型, 尺寸, 位置} 中为 conflict 的字段
required    = {类别, 车型, 尺寸} 都 equal，位置为 equal 或 n/a，且除 OE 外无任何缺失（含车型年份）

if shared_oe 且 跨供应商:
    无 hard 且 required  → auto_confirmed  (AUTO_OE_FULL_MATCH)
    有 hard              → suspect  (SHARED_OE_CONFLICT)
    否则                 → suspect  (SHARED_OE_INCOMPLETE)     # 缺字段
elif 有 hard:
    shared_oe（同供应商）→ suspect  (SHARED_OE_CONFLICT + SAME_SUPPLIER_DUP)
    否则                 → auto_rejected (DIFFERENT_CATEGORY / POSITION / FITMENT / DIMS)
elif shared_oe 或 (类别 equal 且 (车型 equal 或 尺寸 equal)):
    → suspect，原因：OE_DIFFER（双方 OE 都有但不同）/ NO_OE_ATTR_MATCH（至少一方无 OE）
      同供应商再加 SAME_SUPPLIER_DUP；缺关键字段再加 MISSING_KEY_FIELDS
      # 同一供应商的两个编号可能是不同品质档：永不自动合并
else:
    → 不生成候选
  • auto_confirmed → status=accepted（decided_by=rule），可人工撤销。
  • suspect → status=pending，进入待确认清单，排序按：共用 OE 冲突 > 共用 OE 不完整 > 无 OE 属性一致 > 同供应商疑似；同级按置信度降序。
  • auto_rejected → status=rejected（decided_by=rule），不进入人工清单，但在 Admin 中可查，用于说明“为什么没合并”。
  • 条目只有类别、缺车型且缺尺寸 → 不生成候选，记 INSUFFICIENT_FOR_MATCHING（如 A-025），归入“待补充”。

5.4 聚类与防传递误合并

  • 所有 status=accepted 的候选（规则自动 + 人工确认）构成图，用并查集求连通分量，每个分量是一个产品。
  • 防传递：规则产生的合并边在合并两个分量前，检查跨分量的任意两条目：存在硬冲突，或来自同一供应商（同供应商不自动合并的规则在传递时同样生效），则不做该次合并，写 CLUSTER_CONFLICT Issue，把该边降为 suspect（优先级 1）。人工确认的合并边视为权威，不受此检查限制。
  • 例：增量演示中 A-028 与 A-005 同属供应商 A、共用 OE-VNL-1005；B-005 ↔ A-028 满足自动归一，但会把 A-005 与 A-028 带进同一产品，因此被暂停并交人工确认。
  • 以簇为节点生成候选：已属于同一产品的条目，对外只保留得分最高的一对候选，避免同一问题出现 N 次。复核一次即对整个簇生效。
  • 编号稳定：分量沿用其中最早创建的产品编号；被并入的产品标 retired 并指向 merged_into；拆分时新分量获得新编号。

6. 人工复核与回写

  • 匹配运行方式：每次导入或复核后，对全库按分块（blocking）重新评估候选（Demo 规模下为毫秒到秒级）；规则产生的决定随之刷新，人工决定按 evidence_hash 保护。
  • Web 复核队列 /review/：按优先级列出 pending/needs_info 的候选；详情页并排展示双方的归一属性、字段比较结果（相等/冲突/缺失着色）、原始行与来源定位、建议动作；操作：确认合并、不是同一产品、待补充资料，必须填写备注才能对存在硬冲突的候选确认合并。
  • 撤销 / 拆分：产品详情页列出归一依据（每条已合并的边），进入该边选择“不是同一产品”，即改为 rejected（decided_by=human）并重新聚类；Admin 中也可批量操作。
  • 离线回写：review_list.xlsx 的“疑似重复”表带 candidate_id 与空白的 decision（merge / reject / needs_info）、note 列；“异常”表带 issue_id 与 decision（resolve / ignore）。import_review 命令校验后回写，未知 ID 或非法取值逐行报错、整体不提交。
  • 人工决定优先：候选保存 evidence_hash（双方当前归一属性的哈希）。重跑规则时，如果人工决定的 evidence_hash 未变，保持人工决定；变了则重新打开（status=pending），并写 ReviewDecision(action=reopened, via=system) 说明“某字段由 X 变为 Y”。
  • 审计：所有决定（包括规则自动决定的首次产生、系统重新打开）写入 ReviewDecision，含操作人、渠道、备注、决定时的快照。

8. 取舍汇总

决定得到放弃
自动归一仅限跨供应商 + 共用 OE + 关键属性全一致误合并风险极低，可解释召回率：大量真实重复需要人工确认
同供应商内部永不自动合并避免把同一家的不同品质档合并同家重复录入需要人工清理
包装尺寸只作辅助证据、排序后比较摆放方向不同不误报冲突无法区分真正长宽互换的不同件（需其他字段兜底）
不换算币种不引入汇率的不确定性不能直接给出“最便宜的供应商”
以簇为节点生成候选复核量可控候选对的“代表对”可能随聚类变化；人工否决按成员对记录以保持有效
不使用 pandas 读取保留原始文本与精确行号多写少量解析代码
规则参数外置 YAML业务侧可调、带版本配置错误需校验（加载时 schema 检查）

9. 已知局限

  • PDF 只支持带文本层的表格；扫描件需 OCR（未实现），此时会产生 UNPARSEABLE 异常提示人工处理。
  • 车型解析基于品牌词表与“车型 + 年份”格式；非常规写法（如 “VNL 670/780”）可能只识别到品牌，此时车型比较结果为 missing（不会误判为相等）。
  • 同义词为有限词表；未知类别不会参与自动归一，只会进入“待补充”。
  • 多个复核人同时处理同一候选时后提交者覆盖（有审计记录）；未实现乐观锁。
